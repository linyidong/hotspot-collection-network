## 1. 为什么采集层必须复用

**【事实】** `china-finance-rss` 已经把财联社、东财、同花顺、金十、华尔街见闻的公开端点封装成标准 RSS，MIT 许可，本地 `python server.py` 就跑起来。

自己重写等于重新踩一遍反爬、编码、时间格式的坑，收益为零。**这一层能用别人的就用别人的。**

## 2. 为什么不直接用 TrendRadar

它确实很强（63k star、35 平台、AI 筛选、推送、Docker），但：

1. **许可证是 GPL-3.0**：一旦复制代码进项目，永久限死「只能自用、不能分发」。虽然当前符合，但堵死了未来。
2. **它解决的是「聚合 + 推送」，不是「商机加工」**：核心需求它不覆盖。
3. **技术栈是 Python + GitHub Actions 推送流**，我们要的是常驻服务 + 大屏。

**结论：只借它的平台清单与配置思路，不引入它的代码。**

## 3. 为什么加工层必须自研

**【事实】** 调研范围内，所有工具的输出都停在「摘要 / 翻译 / 情感 / 热度排序」。

用户的判断锚点（越南手机壳案例）要求输出：**谁在缺什么 → 缺口能否用数据验证 → 我下一步该查什么/联系谁**。

这一跳没有任何现成实现。它是产品成立与否的关键，也必须由我们自己控提示词。

## 4. 可复用的技术组件（非项目类）

| 需求 | 选型建议 | 说明 |
|---|---|---|
| RSS 解析 | 任意语言内置库 | 不引入重框架 |
| 轻量地球 | ECharts GL / 纯 CSS 贴图旋转 | v1 优先纯 CSS 或 canvas，避免大依赖 |
| 图表 | ECharts | 金价/油价/汇率折线 |
| 调度 | 系统定时任务 / 进程内定时器 | 不引入 Airflow 这类重家伙 |

> 具体技术栈在阶段 5 定稿，本表只记录「复用 vs 自研」的结论。
