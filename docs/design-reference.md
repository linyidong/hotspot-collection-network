## 2. 为什么不能直接「融合代码」

**（1）前两个仓库没有许可证。**

GitHub 上「没有 LICENSE 文件」不等于「随便用」。按著作权法默认保留所有权利——可以看、可以学，**不能复制代码进自己项目**，无论是否商用。这与 `AGENTS.md` 的许可证边界一致（我们已经因为 GPL 拒绝过 TrendRadar 的代码）。

**（2）技术栈冲突。**

三个都是 React/TypeScript + 构建链。本项目的硬约束是**零构建前端**（用户不会维护 npm）。为了「融合」而引入 React + Vite，等于把最脆的一环交给最不会修的人。

**（3）第三个仓库跟需求无关。**

CodexMonitor 是给开发者看 AI 编码代理状态的，MIT 许可很友好，但方向完全不同。唯一可借的是 Tauri 打包思路（把网页包成桌面应用），而我们的方案是本地服务 + 浏览器，**不需要**。

## 3. 那我们「融合」什么

**融设计，不融代码。** 从截图与两个同类项目里，吸收这 5 个信息架构元素：

| 元素 | 来源 | 我们怎么用 |
|---|---|---|
| 左侧可折叠「图层 / 筛选」抽屉 | 截图左下 | 时间窗（1h/6h/24h/48h/7d/全部）、阶段（S1–S4）、行业（宠物/母婴/数码…）、等级（A/B/C） |
| 顶部工具条 | 截图顶部 | 时钟、运行状态灯、数据源健康（5 源亮/灭）、一键采集、今日花费/余额 |
| 中央地图 + 打点 | 截图中央 | **保留圆形地球**（用户明确要求），打点颜色按阶段区分 |
| 右侧面板网格 | 截图右半 | 按阶段分组的卡片面板 + 状态徽标（实时 / 待审 / 不可用 / 已排除） |
| 底部状态条 | 截图底部 | 版本、光点数、源健康数、本轮耗时 |

**不吸收的**：它们的配色、它们的品牌元素、它们的平面地图（我们坚持圆形地球）、它们的 React 组件库。
