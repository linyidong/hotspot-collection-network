# 知识库检索 + AI 总结（RAG Demo）

把热点采集网络 5 天攒下的数据变成一个**能问答的知识库**：输入问题 → 检索出相关线索 → 模型只基于这些线索作答，并强制标注来源编号。

用一句话说明为什么做它：原来这些数据只能「看」，不能「问」；而「知识库检索 / 客服工单」正是 AI 应用岗最高频的落地场景。

---


## 三、三个设计取舍（面试可讲的就是这几条）

### 1. 为什么不用向量库，用 SQLite FTS5

| | FTS5 + 中文二元组 | 向量检索 |
|---|---|---|
| 依赖 | 0（Python 自带 sqlite3） | 需要 embedding 模型/服务 |
| 离线 | ✅ 完全离线 | ❌ 建索引要联网 |
| 可解释 | ✅ 命中哪些词、分数多少都看得见 | ❌ 只能看相似度 |
| 语义泛化 | ❌ 同义词不命中 | ✅ |

结论：**这个场景（情报检索）用户要的是「哪条资料支撑了这句话」，可解释性比语义泛化重要**，加上本机网络不稳，选 FTS5。
局限也写进第五节——同义词召回差，下一步混检索。

**中文怎么切**：FTS5 自带的 `unicode61` 不切中文，整句会被当做一个词。所以索引和查询都把中文切成 **bigram**（`锂电池` → `锂电 电池`），英文/数字整词保留。同一个 `tokenize()` 函数两边共用，否则一定对不上。

### 2. 三个踩出来的坑（都已修，代码里有注释）

| 坑 | 现象 | 修法 |
|---|---|---|
| 疑问词污染召回 | 查「锂电池出海**有没有**机会」，把「人民日报：上技校**有没有**用」召回了 | 停用 bigram 表（`有没/哪些/什么/最近…`），查询前丢掉 |
| url 去重被骗 | 同一篇文章被 3 个批次重复分析，结果里出现 3 条几乎一样的卡片 | 去掉 url 里的快照参数也未必干净，干脆按**规范化标题**去重 |
| OR 拼出来的噪声尾巴 | 所有 bigram 用 OR 连，尾部会带出分数很低的无关条目 | 相对分数截断：只保留 ≥ 最佳结果 45% 的 |

### 3. 检索与生成彻底分离

```
/api/search  → 只检索，11–14 ms，离线可跑
/api/answer  → 检索 + 调模型，模型挂了也照样返回命中的资料
```

这不是为了好看：**情报工具最怕「模型一挂，整个页面变白」**。资料是硬资产，模型只是组织语言。

Prompt 里两条硬约束：

- 每条结论必须标 `[编号]`，回答里不带编号视为不合格；
- 资料不足必须说「资料不足」，并指出还缺什么，**禁止用常识补成事实**。

实测效果（问「出口退税下调对哪些品类有影响」）——模型只对资料里明确提到的电池品类下结论，对家电那条主动说「[2] 提到的是关税下调，不能作为出口退税下调影响家电的依据」，然后列缺口。**这是 prompt 起作用，不是模型天生谨慎。**

## 五、评测：怎么知道检索真的变好了

```powershell
python eval\run_eval.py --k 5     # 20 条固定问题 × 4 组配置，输出 eval/REPORT.md
```

问题集 `eval/questions.json`：**20 条问题，覆盖 6 个业务场景**（关税/退税、储能、上游原料、榜单选品、跨境市场、政策、细分需求）。判定用「title + 完整正文包含关键词」——**这是关键词命中，不是人工相关性标注**，报告里写明了它偏宽松。

同批问题跑 4 组配置（关掉停用词/去重/截断即"改动之前的行为"）：

| 配置 | hit@1 | hit@3 | MRR | 噪声率 | **重复率** |
|---|---|---|---|---|---|
| A 改动前 | 95% | 95% | 0.950 | 27% | **40%** |
| B + 停用词 | 95% | 95% | 0.950 | 26% | 40% |
| C + 去重 | 95% | **100%** | **0.967** | 28% | **0%** |
| D 全开（默认） | 95% | 100% | 0.967 | 26% | 0% |

**这张表最重要的不是"提升了几个点"，是它推翻了我的一个判断**：

- **去重被明确验证**：重复率 40% → 0%。改动前 top-5 里四成是同一篇文章的不同批次分析，用户会以为"只有这几条"。
- **停用词与截断的收益在这套判定下几乎看不见**（噪声 27% → 26%，hit@1 一点没动）。不是它们没用，是**判定太宽松**——只要出现"锂电池"就算命中，"港股锂电池板块下跌"这种低信息量的卡也算对。它们真正的战功是把「上技校有没有用」这类**完全无关**的热搜挡在门外，而这个现象在关键词判定里根本看不见。

结论：**关键词判定能防"越改越差"，但测不出"改动解决了哪类错误"**。所以第一步不是继续调参，是给 20 条问题人工标 0/1/2 三档相关性（下一步，见 REPORT.md 末节）。

> 附带的坑：第一版评测用 `excerpt`（窗口片段）判定，Q15 明明命中了却被判未命中——窗口截断会造假阴性。改成按完整正文判定后 hit@1 从 85% 升到 95%，**升的不是检索，是评测本身的 bug**。

## 七、已知局限（主动说，别等被问）

| 局限 | 影响 | 下一步 |
|---|---|---|
| 无同义词/近义扩展 | 问「动力电池」可能漏掉只写「锂电池」的资料 | 混检索：FTS5 召回 → embedding 重排（先做重排，不重建索引） |
| 评测是关键词判定 | 偏宽松，测不出"噪声类"改动 | **人工标注 20 条 0/1/2 相关性，重算 nDCG（第一优先）** |
| 没评生成侧 | 只评了检索，回答是否编造没量化 | 规则校验引用编号 + 抽检 30 条 |
| 没有 rerank 与切片 | 长文档只截一段窗口，可能漏掉关键句 | 按 `fact/signal/next_action` 分段入库，按字段检索 |
| deep 线索卡只有 304 条 | 高价值语料偏少，问答深度受限 | 回补 deep 阶段（当初 6,080 条被 skip） |
| 单机单文件索引 | 不支持并发写 | 只读场景够用；要增量就换 DuckDB/ES |
| 没有权限与引用溯源到原网页 | 企业场景不可用 | 加来源 URL 存证 + 访问日志 |

## 八、面试怎么讲（四句话）

1. **「我把 2.8 万条采集数据做成了能问的知识库，检索 12–16 毫秒、离线可跑。」**
2. **「我特意没用向量库：这个场景用户要的是『哪条资料支撑这句话』，可解释性比语义泛化重要；本机网络不稳，FTS5 零依赖更可靠。」**
3. **「我给它建了评测集：20 条问题跑 4 组配置。结果最有用的一条是——它证明我那个『去重』真有用（重复率 40%→0），也证明我另外两个改动在这套判定下**测不出来**，所以下一步该做人工标注，而不是继续调参。」**
4. **「结论我敢说得比较硬，是因为我说的是『我测出了什么、没测出什么』，不是『我优化了多少』。」**
